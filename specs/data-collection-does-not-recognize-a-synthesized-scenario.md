# Data collection does not recognize a synthesized scenario

Maintain the invariant conditions in @INVARIANTS.md and fix the following issue:

## Problem

The Business Case Offer produces **two** provenances — `cord` when a CORD
collection fits the chosen category, and `synthesized` when none does. Data
collection's skip guard recognizes only `cord`. So a Bootcamper whose generated
scenario is synthetic is asked, once per source, how they would like to provide
data they already told the bootcamp they do not have.

On this walk that is four sources — CRM, BILLING, SUPPORT, MARKETING — all carrying
`provenance: synthesized`, with `docs/business_problem.md` carrying the
`🤖 Bootcamp-generated business case` marker. Four repetitions of a decision made in
Module 1.

The step's own prose condemns exactly this: "with a six-source generated scenario
that is six questions whose honest answer is *'you already told me this in Module
1.'* Option 5 restates that choice rather than asking anything new about *this*
source, so it is **escapes a literal INV-006 violation while being exactly the
repetition INV-006 exists to prevent**."

And the branch it falls into cannot resolve: option 5's handling "recommend[s] CORD
data as the primary alternative", which is the option Module 1 already evaluated and
rejected for this category.

## Root cause

`plugins/senzing-bootcamp/skills/module-04-data-collection/SKILL.md:141-151` names a
single provenance:

> "If it already records a provenance the Bootcamper chose earlier — **`provenance:
> cord` is the case the Business Case Offer produces** … then the provision decision
> is **already made** for every source in that scenario."

`plugins/senzing-bootcamp/skills/module-01-business-problem/phase1-discovery.md:136-137`
produces both:

> "**Fitting CORD dataset returned:** back the scenario with it, provenance `cord`.
> **None fit:** synthetic data, provenance `synthesized`."

Two further mismatches follow from the same root:

1. **The remedy assumes a download.** The guard's action is "go straight to
   downloading/collecting that source", and it routes to
   [CORD fetch integrity](#cord-fetch-integrity). A synthesized scenario has nothing
   to fetch — the data has to be *generated*, and Module 4 has no branch that
   generates it for an already-decided scenario.
2. **The two modules disagree on what `synthesized` means.** Module 4 lists it as a
   valid provenance value (`:395`, "generated test data") but treats the act as
   "**only as a last resort** after CORD and free-data options are declined"
   (`:806-808`). Module 1 treats it as the correct, expected outcome whenever no
   CORD collection fits the category — which, for the customer-facing categories,
   is the normal case rather than the exception (see
   `specs/truthset-cannot-satisfy-the-generated-scenario-invariants.md`).

## Proposed change

1. **Widen the skip guard to any bootcamp-generated provenance.** The condition
   should be "the scenario was generated by the bootcamp" — evidenced by the
   `🤖 Bootcamp-generated business case` marker plus a recorded provenance of `cord`
   **or** `synthesized` — not by `cord` alone. State the marker as the primary
   signal and the provenance as what selects the *action*, which is the distinction
   the step currently conflates.
2. **Add the synthesized action.** When provenance is `synthesized`, the step's job
   is to **generate the source files** into `data/raw/` from the scenario recorded in
   `docs/business_problem.md` and `config/data_sources.yaml` — the record counts,
   entity types and per-source quirks are all already written there — and to say so.
   No question, no CORD recommendation, no free-data hierarchy: that hierarchy is for
   a Bootcamper who has *not* already decided.
3. **Reconcile the "last resort" framing at `:806-808`.** It is correct for a
   Bootcamper arriving with no data and no scenario; it is wrong for one whose
   generated scenario is synthetic by design. Scope it to the former.
4. Make the generated files consistent with what Module 1 promised — the mapping
   complexity Step 4a's invariant required (names split one way in one source and
   joined in another, addresses in free text, per-campaign duplicates) — so Data
   Quality, Mapping, and Transformation has the work the scenario advertised.

## Acceptance criteria

- [ ] A run whose sources carry `provenance: synthesized` and whose
      `docs/business_problem.md` has the generated marker asks **no** provision
      question for any source.
- [ ] That run produces the source files in `data/raw/`, one per source, with the
      record counts recorded in `config/data_sources.yaml`.
- [ ] A run with `provenance: cord` behaves exactly as it does today.
- [ ] A Bootcamper with no scenario and no data still gets the full CORD →
      free-data → synthesize hierarchy.
- [ ] The generated files carry the mapping complexity the scenario described, so
      the mapping module has real work.
- [ ] Holds on Linux, macOS, and Windows and stays language-agnostic (per @INVARIANTS.md).
