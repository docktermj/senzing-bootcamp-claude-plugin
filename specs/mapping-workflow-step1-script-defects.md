# Three defects in `mapping_workflow`'s step-1 scripts silently corrupt or lose a source profile

Maintain the invariant conditions in @INVARIANTS.md and fix the following issue:

## Problem

`mapping_workflow` step 1 ships the profiler (`sz_schema_generator.py`) and emits the commands to
run it. Three defects were observed across four end-to-end mapping runs. They are grouped here
because they share one delivery channel, one plugin-side remedy — document the limitation and the
workaround where the step presents it — and one failure signature: **each produces a plausible,
well-formed artifact that is wrong, rather than an error.**

**A — the step-3 field-count warning fires on every correct mapping.** All four runs exited step 3
with "mapped N fields … but profile reported M fields" while every source field was dispositioned:

| Source | Warning | Reality |
|---|---|---|
| `OPENSANCTIONS_PEP` | mapped 14 vs 16 | 6 ignore + 3 feature + 2 payload + 1 discriminator + 4 overrides = 16 |
| `OFAC_SDN` | mapped 13 vs 12 | 12, all dispositioned |
| `ICIJ` | mapped 10 vs 7, and 26 vs 21 | 7 and 21, all dispositioned |
| `UK_COMPANIES_HOUSE` | mapped 58 vs 55 | 55, all dispositioned |

The counter includes `derived` entries — `RECORD_ID`, `DATA_SOURCE`, `RECORD_TYPE`, `REL_ANCHOR`,
`REL_POINTER` — which are **not source fields**, while excluding fields declared only inside
`type_discriminator.field_overrides`, which **are**. The two errors do not cancel: 12 → 13 high,
16 → 14 low. Both `derived` and `type_discriminator` are prescribed by the workflow itself — the
live `mapping_workflow` schema (server 1.32.3, verified 2026-07-31) declares `derived` with a
`derived_as` enum of exactly those five values, and declares `type_discriminator` as a step-3 field.
So every mapping that follows the guidance trips it, which trains the reader to ignore a step whose
*other* warnings are real.

**B — two profiler commands write to the same output path.** Starting a run with two input files
returned:

```text
python3 data/mapping/sz_schema_generator.py data/raw/icij/nodes-officers.csv -o data/mapping/profile_report.md
python3 data/mapping/sz_schema_generator.py data/raw/icij/nodes-entities.csv -o data/mapping/profile_report.md
```

Run as issued, only the second file's profile survives. Step 3 then tells the reader to consult
`profile_report.md` for how "each source file" is structured, and half of it is gone. The file
exists, is well-formed, and describes one schema — so a mapper written against it looks correct
until fields from the lost schema come back blank.

**C — the profiler cannot read a headerless CSV, and the recommended catalog ships one.**
`samples/raw/ofac-sdn/sdn-sample.csv` from the free-data repository is headerless; its own README
documents 12 positional columns. The profiler assumes a header row, so it consumes the first data
row as column names: **one sanctioned party disappears** and every column is mislabelled with a value
from that row. A mislabelled profile does not fail — it produces a confident, wrong mapping.

A secondary observation from the same file: `-0-` is OFAC's null sentinel and, being a value, makes
the profiler report **100% population on all 12 columns** when 8 carry no information. Any
completeness score derived from population rates this source perfect — the INV-128 class, one layer
upstream.

## Root cause

All three are in MCP-delivered artifacts, not in the plugin: the counter and the command list are
generated by `mapping_workflow`, and the profiler is the script it ships. The plugin's exposure is
that step 3 and step 4 present these outputs as authoritative without naming what they cannot do.

The plugin already maintains exactly this kind of limitation list for the sibling gate at
`module-05-data-quality-mapping/phase2-data-mapping.md:330-361` — including one entry recording a
gap **since fixed upstream** (`:342`, "Numbers are NOT in that list any more"). That is the shape to
extend, and it is why these belong in one spec: the remedy is three more entries in a maintained
list, not three separate changes.

## Proposed change

1. **Document the field-count warning as expected** when a mapping uses `derived` entries or a
   `type_discriminator`, with the arithmetic that explains it, so a reader can tell this warning from
   the step's real ones. Do **not** tell them to suppress warnings generally.
2. **Instruct profiling to distinct output paths** for a multi-file source — `profile_report_<stem>.md`
   — and to concatenate, since the emitted commands collide. Say why: the collision is silent.
3. **Name the headerless-CSV limitation** at the point the profiler is run, with the workaround the
   bootcamper used: write a headered copy for profiling only, using the documented column order,
   while the mapper still reads the raw file positionally. Warn that a dominant sentinel token (OFAC's
   `-0-`) inflates population to 100%, so a completeness figure from the profile is not a quality
   signal (INV-128).
4. **Keep all three as upstream-owned.** The plugin documents and works around; it does not fork the
   profiler (INV-173's no-fork rule) and it re-checks whether each is still needed, exactly as the
   numeric-value entry was retired when the server fixed it.

⚠️ **Do not present the workarounds as the normal route.** Each is a concession to a current tool
limitation. Framed as best practice they outlive the defect, and the numeric-value entry shows these
do get fixed.

## Acceptance criteria

      rule that produces it, and the step still directs the reader to read its other warnings.
- [ ] Multi-file profiling is instructed to distinct output paths, with the silent-overwrite reason
      stated.
- [ ] The headerless-CSV limitation and its headered-copy workaround appear **where the profiler is
      run**, not only in a limitations list elsewhere (INV-183).
- [ ] The sentinel-token caveat is stated wherever the profile's population figures could feed a
      completeness judgement, cross-referencing INV-128.
- [ ] Each of the three is marked upstream-owned with a date, so a later run can retire it when the
      server fixes it — the shape `:342` already uses.
- [ ] No forked copy of `sz_schema_generator.py` ships (INV-173).
- [ ] A test asserts all three limitations are documented, so none can be dropped silently.
- [ ] **Not runtime-verified:** none of the three was reproduced this session — that needs a live
      `mapping_workflow` run with a workspace and multi-file/headerless sources. What was re-verified
