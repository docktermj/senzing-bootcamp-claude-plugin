# Invariants

The following is the canonical list of invariants for the Senzing Bootcamp
Claude Plugin (SBCP). They are aspects of the SBCP that must **ALWAYS** be true.
Every spec under `specs/` begins "Maintain the invariant conditions in
@INVARIANTS.md" — no spec may be implemented in a way that violates any invariant
below.

Each invariant has a **stable ID** (`INV-NNN`). The ID is a permanent address:
specs, feedback triage, and audits reference invariants by ID, so IDs are never
renumbered or reused. New invariants are appended (see
[Maintaining this file](#maintaining-this-file)); existing ones are only edited
in place, never removed.

For hints when implementing the features these invariants describe, the Senzing
Bootcamp for Kiro Power may be consulted. Use the appropriate Claude Plugin
techniques to implement the features captured in the Kiro Power hook files and
steering files.

- Repository: <https://github.com/docktermj/senzing-bootcamp-kiro-powers/tree/main>
- Kiro Power: <https://github.com/docktermj/senzing-bootcamp-kiro-powers/tree/main/senzing-bootcamp>

## Maintaining this file

This file is machine-extended: as specs are implemented, the guarantee a spec
establishes becomes an invariant that all future work must maintain. The
`implement-spec` skill appends those invariants here. To keep the file
deterministically extensible, follow these rules:

1. **Never delete or renumber an existing invariant.** IDs are permanent
   references. If an invariant becomes obsolete, mark it (e.g. append
   "(superseded by INV-NNN)") rather than removing it.
2. **Editing an existing invariant** is allowed only to clarify wording without
   changing its meaning. A change of meaning is a *new* invariant with a new ID.
3. **To add an invariant**, append it under
   [Invariants added from implemented specs](#invariants-added-from-implemented-specs)
   using the **next unused `INV-NNN`** — that is, one greater than the highest
   `INV-NNN` anywhere in this file (zero-padded to three digits). Record its
   provenance (the spec that established it and the date).
4. **Phrase every invariant as a single, testable MUST/ALWAYS condition.** If a
   spec establishes several, add one invariant per condition.
5. The `## Invariants added from implemented specs` heading and its append marker
   below must be preserved so tooling can locate the insertion point.

## INV-001 – INV-004: Foundational constraints

These apply to the SBCP as a whole and to every module, spec, and artifact.

- **INV-001** — The SBCP MUST run on the following platforms: Linux, macOS, and Windows.
- **INV-002** — The SBCP MUST be programming-language agnostic.
- **INV-003** — The SBCP MUST be consistent, coherent, and complete.
- **INV-004** — The SBCP MUST be production-ready.

## INV-005 – INV-015: Whole-Bootcamp outcomes

When the Bootcamper runs the SBCP, these MUST hold across the entire Bootcamp.

- **INV-005** — Each question to the Bootcamper is preceded by "👉".
- **INV-006** — Each question is asked only once, unless the Bootcamper asks to have the question repeated.
- **INV-007** — All questions MUST be answered by the Bootcamper. The plugin cannot answer questions nor assume answers.
- **INV-008** — Questions are not ambiguous with respect to a "Yes" or "No" answer.
- **INV-009** — Questions are not "complex". The use of "or" is discouraged.
- **INV-010** — At any time, a Bootcamper can submit "Bootcamp feedback:".
- **INV-011** — At any time, a Bootcamper can change the verbosity of the Bootcamp.
- **INV-012** — All output MUST be relative to the Bootcamper's point of view. Output that is not important to the Bootcamper is suppressed.
- **INV-013** — All shipped modules are performed in order: Module 1 → 2 → 3 → 4 → 5 → 6 → 7. (Advanced Topics — performance, security, monitoring, deployment — ship as production-hardening follow-ups delivered at graduation, not as separate numbered Modules 8-11.) (An optional, non-counted Module 0 preamble is exempt from this ordering — see INV-072.) (Superseded by INV-076: Core runs all modules in order; Customized runs the selected subset in prerequisite order.)
- **INV-014** — Modules are not skipped unless requested by the Bootcamper. (Skipping the optional Module 0 preamble is a permitted, requested skip — see INV-072.) (Customized module selection is such a request: an optional module the Bootcamper does not select is a requested skip — see INV-076.)
- **INV-015** — Submitted bootcamp feedback is captured in `docs/feedback/SENZING_BOOTCAMP_PLUGIN_FEEDBACK.md`.

- **INV-169** — A single observation of SDK behavior MUST NOT be generalized into an absolute about a *method*. Where behavior varies with flags, version, or binding, the guidance MUST record what was observed together with the flag set, SDK version and binding it was observed under, and MUST route the reader through a per-installation check (dump one row and read it) rather than asserting the outcome. Stating an over-generalized absolute is worse than stating nothing: it teaches that a correct approach is broken, and a reader who meets a contradicting MCP source has no way to adjudicate without dumping a row themselves. Where an MCP tool documents the behavior, that citation governs and MUST be given (INV-080); the dumped row remains the authority for what a given installation actually returns (INV-115/INV-149). Observed twice: `SZ_EXPORT_ALL_FLAGS` was shipped as "does not exist" and needed a five-place retraction (INV-132), and phase D shipped "do not expect `RELATED_ENTITIES` from `export_json_entity_report`" — false under `SZ_EXPORT_DEFAULT_FLAGS`, and contradicted by `reporting_guide(topic='evaluation')`. (Source: `export-related-entities-is-flag-conditional`, 2026-07-28.)
- **INV-168** — A helper that discovers an external executable MUST search each supported platform's conventional install locations, not only `PATH` plus one platform's absolute paths, and MUST expand those locations from the environment rather than hard-coding a drive letter or a localizable directory name. It MUST NOT report a capability as absent when it is present, and when it does report one absent it MUST name the locations searched — being told to install software one already has is worse than "not found", because it sends the reader to fix the wrong thing. A run where the executable was **found** but the operation still produced nothing MUST be reported distinctly from one where nothing was found (extending INV-122's reason-distinguishing rule to a third case). Where the capability is genuinely missing the helper still degrades per its own contract and MUST NOT install anything to satisfy itself (INV-122, INV-129). Observed: Windows places neither Chrome nor Edge on `PATH`, so a Windows 11 workstation carrying both was told no screenshot capability was available and lost every recap screenshot, while `C:\Program Files\...` was never examined. (Source: `windows-headless-browser-discovery-for-screenshots`, 2026-07-28.)
- **INV-167** — Where the SBCP offers a PowerShell counterpart to a shell command, that counterpart MUST use PowerShell syntax and MUST NOT carry bash-shaped constructs: no `&&`/`||` chaining (use `A; if ($?) { B }`), no `if` used as an expression, no ternary or null-coalescing, no heredocs, and no inline `python -c`. Multi-line or quote-heavy code MUST be placed in a script file under `src/` (INV-018) and run as a file. Each of these is a *parser* error on Windows PowerShell 5.1 — the default `powershell.exe` on Windows 11, whose limits the plugin's guidance MUST assume unless it has verified `pwsh` 7+ — so the message points at syntax rather than at the real cause, which is a command written for another shell. (`tests/test_windows_powershell_guidance.py` sweeps every PowerShell block for `&&`/`||` and MUST pass.) (Source: `windows-powershell-encoding-and-syntax`, 2026-07-28.)
- **INV-166** — Every file the Bootcamp writes MUST be byte-correct UTF-8 with no BOM, and generated files MUST be written through Python or the agent's file tools rather than PowerShell redirection. On PowerShell 5.1 `-Encoding utf8` writes a BOM and `Get-Content` without `-Encoding` decodes as the system ANSI codepage, and both corruptions are invisible to every obvious check — a BOM makes only record 1 of a JSONL fail (reading as one bad source record rather than an encoding fault), and a double-encoded document is valid UTF-8 containing no U+FFFD, merely wrong. Windows-1252 mojibake MUST therefore be detected and reported over `docs/*.md` before the recap renders, and **reported rather than silently repaired**, since a repair is a content change and the normalizer's contract is that it changes formatting only (INV-110). (Source: `windows-powershell-encoding-and-syntax`, 2026-07-28.)
- **INV-165** — An example, hint, or suggested query offered to the Bootcamper MUST be verified by **actually running it** and MUST return at least one result; deriving it from real loaded data is NOT verification. One that returns nothing MUST be dropped with a reported reason (stderr at build time, `console.warn` in a live page), never shipped as a dead control — a hint that finds nothing is worse than no hint, and it also silently misattributes a query defect to the Bootcamper's data. Observed: every Search / Probe chip named after an organization was a real merged entity and still returned nothing, because search tried `NAME_FULL` only (INV-164). (Enforces the "pre-verified" claim the visualization contract already made. Source: `organization-search-requires-name-org`, 2026-07-28.)
- **INV-164** — A name search the Bootcamp performs or generates MUST NOT use `NAME_FULL` alone: it MUST also try `NAME_ORG`, because per the Senzing Entity Specification (Name > Feature: NAME) `NAME_ORG` is the organization name attribute while `NAME_FULL` is the single-field attribute for a name whose type is unknown — so an organization name sent as `NAME_FULL` matches nothing **and raises no error**. The response MUST report which attributes were tried, and a zero-result search MUST be rendered as "nothing matched the attributes tried", never as absence from the data (INV-115). This binds a visualization or query program in **any** language (INV-090/INV-124), not only the bundled Python reference: the defect reached a generated query program precisely because it lived in the reference implementation and in no written rule. Observed on a half-organization dataset, where search silently failed for about half the population. (Source: `organization-search-requires-name-org`, 2026-07-28.)
- **INV-163** — A verification check that cannot run because its tool is absent MUST be recorded as skipped, naming the check, and any completion or closing message MUST state which verification steps did not run; an artifact MUST NOT be described as verified for a check that did not execute. Where a check's tool is not present on every supported platform — poppler (`pdftoppm` / `pdfimages` / `pdfinfo`) is absent on Windows by default, so the page raster and the honest image count are exactly the checks a Windows run loses — the guidance MUST offer a route needing no new dependency, since INV-129 forbids installing one to satisfy a check. Concretely for the recap PDF: the generator's own embedded-image count, then Pillow (already present via `fpdf2` in the project-local venv of INV-066), before `pdfimages -list`, and the `/Subtype /Image` grep last and labeled as overcounting. A skipped check never blocks (INV-048, INV-052/INV-066) and this stays agent-side apparatus, not Bootcamper-facing output (INV-012). (Extends INV-129 from performing verification to reporting its coverage: a keepsake whose layout nobody could inspect is acceptable, one described as verified when its layout was never inspected is not. Source: `pdf-layout-verification-without-poppler`, 2026-07-28.)
- **INV-162** — A generator that drops a referenced asset from a deliverable MUST report each drop on stderr, distinguishing "not found" from "found but unusable", and MUST report an embedded-of-referenced count alongside any content-retention figure. A character-retention figure structurally cannot see a missing image — the characters do render — so retention alone MUST NOT be presented as evidence of a complete artifact: a recap that lost all six of the Bootcamper's screenshots reported `rendered 46707 of 46973 source characters (99%)` and exit 0, and the only clue was an implausibly small file. The drop itself stays non-fatal (INV-048); only silence is forbidden. Where a renderer embeds no assets by design (the stdlib fallback), the count MUST say so rather than reading as a lookup failure. (Extends INV-110/INV-111 from characters to embedded assets. Source: `recap-pdf-images-resolve-against-recap-directory`, 2026-07-28.)
- **INV-161** — A relative asset reference inside a generated deliverable's source document (e.g. a recap `![alt](path)`) MUST be resolved against **that document's own directory**, never against the process working directory. The path that is correct for reading the source in a Markdown renderer MUST also be correct for rendering it, so an author following the instruction cannot produce a lossy artifact, and no step may require a `cd` to make assets resolve. (Before this, `generate_recap_pdf.py` resolved against `Path.cwd()` while graduation ran it from the project root, so document-relative screenshot paths silently resolved to nothing and no path satisfied both the Markdown recap and the PDF. Source: `recap-pdf-images-resolve-against-recap-directory`, 2026-07-28.)
- **INV-160** — Where an MCP tool's response carries **both** a payload field and metadata describing that payload's size or completeness, a payload that contradicts its own metadata MUST be treated as a **failed retrieval**, never as a real empty result: concretely, `find_examples` file retrieval (`repo` + `file_path`) returning an empty `content` alongside a non-zero `content_length` means the retrieval failed, and `truncated: false` MUST NOT be read as confirming completeness. The guide MUST fall back to the response's own documented access path (fetch `raw_url`, or clone per `access_steps`) and MUST NOT tell the Bootcamper an example file is empty, or silently skip the example, on that basis. An undeclared parameter MUST NOT be adopted as the remedy even when the response's own prose advertises one — only parameters the live schema declares may be passed (INV-136). This does **not** conflict with INV-149: an empty result with *no* contradicting metadata (an empty `response_schemas` `data` array) is coverage, not failure — it is the contradiction that signals the defect. Verified 2026-07-28 against server 1.32.1. (Source: `find-examples-file-retrieval-returns-empty-content`, 2026-07-28.)
- **INV-159** — A generator MUST NOT reduce any character of a Bootcamper-authored value to `?`, and this MUST hold for the Bootcamper's **name** specifically — the string INV-134 detects from `git config user.name` and the Certificate of Completion prints largest. Characters outside the built-in fonts MUST be folded to a readable ASCII equivalent where one exists (including Latin letters with no NFKD decomposition — `Ł ł Đ đ Œ œ …`, whose loss changes the name rather than degrading it) and otherwise **dropped**, never encoded. A name in a non-Latin script MUST NOT be transliterated by the plugin: how it is spelled in Latin script is the Bootcamper's decision, so the generator MUST instead (a) warn on stderr naming the unprintable characters, (b) print the `CERTIFICATE_NAME_PLACEHOLDER` rather than a blank recipient line, and (c) make "not printable in the recap PDF" one of the conditions that triggers INV-113's pinned name question at graduation, where declining still costs nothing (INV-048). The font-safety inventory MUST cover names, not only punctuation and symbols. (Enforces INV-143, whose inventory covered what deliverables carry *except* the most certain thing they carry: a Bootcamper named 李明 had `??` printed on their certificate, silently, at exit 0 — found by the 2026-07-28 deep-dive audit.
